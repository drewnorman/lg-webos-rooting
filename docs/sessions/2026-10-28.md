- TV: LG 50UK6090PUA, firmware `05.50.70`.
- LG CLI `ares-device --system-info`: SDK `4.4.0`, board `LM18A_ATSC_KR`.

- Upstream faultmanager-autoroot commit: `a972c95f4f4dbacdb72215409ea0c9eff39dabc1`.
- `autoroot.sh` SHA-256, verified on both laptop and TV: `66a8a2816567a3c3d29768095873d347ec6bb2cbf60208979d15d7a42525d4d0`.

- TV downloaded these exact files to `/tmp` after its SSH service did not complete `scp` or SFTP transfers.
- `sh /tmp/autoroot.sh` ran on the TV. It reported an empty webOS version from its own version parser, despite the successful LG CLI SDK query above. The expected segmentation fault occurred; the payload then ran as UID 0.
- Output reported `Homebrew Channel has been elevated`, `Rooting complete`, and `Payload complete`. The command exited with status 0.
- The script verified the existing `start-devmode.sh` signature and reported that the LG Developer Mode app was still installed.
- Diagnostic logs were saved under `/tmp`.

## Post-root SSH and baseline preparation

- Drew enabled SSH in Homebrew Channel and rebooted. Port 22 then opened.
- A dedicated 4096-bit RSA key was created at `~/.ssh/lg_webos_root_50UK6090PUA`. Root key login succeeded; `/home/root/.ssh/authorized_keys` had mode `600`, and its directory had mode `700`.
- The laptop's `lg-webos` SSH alias uses that key. A new `lg-root` webOS CLI profile successfully returned the TV's model, SDK, firmware, board, and OTA ID. The old Developer Mode profile and saved passphrase were removed.
- The first post-SSH reboot revealed that Homebrew Channel had started Telnet on port 23. Its disable flag was set and the daemon stopped; port 23 then refused connections.
- After another reboot, SSH key login still worked, Telnet remained closed, the default root password was rejected, and the temporary shadow-file override was absent.
- An early boot snapshot (about one minute after restart) showed 864 MB total RAM, about 209 MB available RAM, 700 MB total swap with about 522 MB free, and load average 6.80. This is not a settled idle measurement or evidence of a performance improvement.
- At about two minutes, load average remained near 6 while CPU was about 71% idle. Six tasks were in uninterruptible wait (mostly platform and device threads), so the load average alone should not be read as CPU saturation.
- With the TV left on Home for about four minutes, 261,656 kB of RAM was available and 641,952 kB of swap was free. A `top` sample showed 81% CPU idle, 217 tasks, and the same six uninterruptible-wait tasks. The writable common-data and appstore partitions were 52% and 39% used. No clear CPU, memory, or storage pressure was evident in this idle snapshot. Remote-control responsiveness and app-launch timings still need manual measurement.
